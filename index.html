UmarTransit-1B

A domain-specific language model for public transit and GTFS data, fine-tuned from Qwen2.5-1.5B with QLoRA.

Project Description
UmarTransit-1B is a 1.54B-parameter language model built specifically to answer questions about public transit systems and GTFS (General Transit Feed Specification) data. It handles the GTFS specification itself — file formats, field meanings, and the relationships between them — alongside real route, stop and schedule data drawn from 15 transit agencies across 10 countries, transfer connections, network statistics and cross-agency comparisons. Ask it what route_type 3 means and it explains bus service; ask how many routes the Chicago Transit Authority operates and it answers 133, broken down into subway and bus. The project was built end to end as an AI/ML engineering exercise, and pairs directly with the transit ticketing platform work that occupies most of my professional time.
My Contribution
Built the entire pipeline solo, from data collection through to a deployed demo. Collected 15 public GTFS feeds totalling 858 MB of raw data, cleaned and normalised them into Parquet (77 million rows, 11,000 routes), then generated a 3,306-example synthetic question-and-answer dataset spanning 8 task categories. Fine-tuned Qwen2.5-1.5B-Instruct using QLoRA via Unsloth on a single Google Colab T4 GPU — three epochs, roughly 30 minutes of training — reaching a ROUGE-L score of 0.82 on evaluation. Published the model and GGUF quantisations to the Hugging Face Hub under Apache 2.0, then built a FastAPI inference backend and a Next.js front end deployed to Vercel with both demo and live-inference modes. Documented the whole build as a step-by-step guide and wrote it up publicly on dev.to and Medium.
Data Provenance
Trained exclusively on publicly available, open-source GTFS feeds published by transit agencies for public use via the Mobility Database. No private, proprietary or NDA-protected data from any client or employer was used at any stage of collection, training or evaluation, and every source feed is documented in the repository.

MemoMind

An AI knowledge engine that turns a team’s documents into citation-backed answers, with semantic search and voice querying.

Project Description
MemoMind lets a team upload its documents and then query them in plain language. Rather than matching keywords it retrieves on meaning, and every answer links back to the specific passage in the specific document it came from, so nothing has to be taken on trust. It searches across an entire document set at once, supports voice interaction for hands-free querying, and isolates documents per user and workspace. It was built to solve a problem my own team had: decisions and context kept getting buried in old project files, and people would re-research things that had already been settled. The moment a colleague used it to recover a technical decision from eighteen months earlier in under ten seconds, it had earned its place.
My Contribution
Designed and built the retrieval architecture. Documents land in Supabase Storage, are parsed and chunked, embedded through the OpenAI embeddings API, and indexed in Postgres using pgvector. A Supabase Edge Function handles semantic retrieval and orchestrates the language model — OpenAI or Claude — to compose an answer with citations attached, plus a spoken response via the Web Speech API. Chose retrieval-augmented generation over fine-tuning deliberately: fine-tuning bakes knowledge into the weights, where it cannot cite a source and goes stale as documents change, whereas retrieval pulls current content at query time and always shows its working. Kept the whole stack on Supabase Edge Functions so that storage, database, vector search and serverless compute live on one platform with no servers to manage. Workspace isolation was built as a first-class feature rather than an afterthought, because a knowledge tool is worthless if users cannot trust that their documents stay their own.
Results
Cut manual document lookup time by over 50% in internal use, with sub-second semantic retrieval across large document sets and support for concurrent users in isolated, secure document contexts. The core engine is functional and in active development; the source is private, with the architecture and design decisions documented publicly.
